# Founder OS Router｜公开路由系统

## Router 负责什么

Router 是 Founder OS 的认知调度层。

它不替代人的判断，也不负责把每句话归档。它只为当前问题组织最少但足够的长期上下文、历史决定、真实证据和已有执行能力，然后说明下一步与结果去向。

```text
当前问题
  → 判断问题属于哪一层
  → 选择需要读取的材料
  → 检查历史决定与真实证据
  → 调用已有能力
  → 形成判断与下一步
  → 决定是否值得长期沉淀
```

## 可以接收哪些输入

Router 可以处理：

- 一个产品想法或功能取舍；
- 一段用户反馈、拒绝或未成交记录；
- 一个增长、定价或商业假设；
- 一次成功、失败或准备停止的实验；
- 一个需要交给 AI 或其他协作者执行的任务；
- 一段希望提炼为长期经验的复盘。

普通资料检索和一次性小问题不必强行进入 Router，也不必形成长期资产。

## 九个判断层

| 层级 | 主要回答 |
|---|---|
| Context | 这项判断与谁的经历、角色和现实条件有关？ |
| Philosophy | 哪些长期价值和原则正在被触发？ |
| Product | 它是否强化核心动作，证据和边界是什么？ |
| User | 用户真正面对的场景、阻力和触发是什么？ |
| Business | 收入、成本、交付和商业边界是否匹配？ |
| Decision | 过去为什么这样选，复查条件是否已经出现？ |
| Experiment | 当前假设、证据、阈值和停止条件是什么？ |
| Capability | 已经有哪些 Prompt、Skill 或工具可以执行？ |
| Workflow | 任务由谁接手、如何验证、结果回到哪里？ |

这些层级是帮助 Router 定位问题的内部地图，不要求使用者记住或手动选择。

## 六步主流程

### 1. 识别任务性质

先判断当前主要是探索、决策、执行交接、实验复盘还是产物交付。

一个任务可以涉及多个方面，但必须先找到当前最主要的矛盾，避免同时展开所有框架。

### 2. 定位拥有层

判断问题主要由哪个层级负责。其他层级只在确实影响结论时补充读取。

### 3. 选择最少上下文

优先读取：

1. 与当前问题直接相关的长期原则；
2. 相似的历史 Decision；
3. 当前项目中的真实数据、行为和反馈；
4. 已经存在的 Prompt、Skill 或工作流。

材料不存在时，明确指出缺口，不得编造过去的判断或证据。

### 4. 选择已有能力

能用现有 Prompt、Skill、模板或工具处理的问题，不因一次任务重复创造新流程。

能力只负责执行，不能代替产品、用户或商业判断。

### 5. 形成当前判断

把事实、推断和价值选择分开，结合现实约束说明：

- 当前更合理的方向；
- 最大取舍和未知；
- 下一项最小证据；
- 谁执行、如何验证、结果放在哪里。

### 6. 决定是否沉淀

先解决当前问题，再判断这次内容是否值得进入长期系统。没有达到门槛的内容继续留在当前项目中验证。

## 路由示例

| 输入信号 | 优先读取 | 可能调用 | 结果去向 |
|---|---|---|---|
| “这个功能要不要做？” | 产品原则、历史功能取舍 | 产品判断框架 | 当前项目；重大取舍进入 Decision |
| “用户为什么需要却不采用？” | 用户阻力、商业边界 | 用户洞察或痛点翻译 | 当前项目；重复验证后升为长期原则 |
| “经验丰富的人为什么拒绝 AI？” | AI 角色、用户控制感、交付边界 | 价值翻译或商业判断 | 案例库；跨场景重复后再沉淀 |
| “这个方向失败了。” | 原始假设、项目数据、停止条件 | Experiment Review | Failure Review 或留在项目 |
| “把任务交给新的 AI。” | 当前目标、边界、状态和验收标准 | 上下文交接模板 | 通常不进入长期系统 |
| “做一份可以真正交付的产物。” | 产物目标、读者路径和质量门槛 | 对应的执行与检查能力 | 文件、测试、截图或检查证据 |

## 最小输出

复杂问题可以使用下面的结构：

```text
问题类型：
当前拥有层：
需要读取：
需要调用：
历史相关决定：
当前判断：
最大取舍或未知：
下一步：
执行者与验证方式：
结果去向：
是否值得沉淀：是 / 否 / 待验证
理由：
```

简单问题可以自然回答，不需要机械展示全部字段；但结果必须让使用者知道当前怎么看、依据是什么、下一步是什么。

## 状态与交接

Router 应让任务在不同阶段之间清楚移动：

```text
探索
  → 已形成可选方案和未决点
决策
  → 已明确选择、范围与停止条件
执行
  → 已明确执行者、文件和验收标准
验证
  → 已获得测试、反馈、数据或其他证据
长期资产
  → 已通过沉淀门槛并拥有明确位置
```

如果执行尚未发生，不能把建议写成已经完成；如果证据不足，不能把愿望写成已验证结论。

## 沉淀门槛

至少满足一项，才建议长期保存：

- 对未来方向或边界有持续影响；
- 在多个不同项目或场景中重复出现；
- 已有真实行为、数据、付费或失败成本；
- 能阻止一个已经发生过的错误再次出现；
- 已形成稳定、可执行、可复查的规则。

否则输出“留在当前项目，等待验证”。

## 新证据如何更新旧原则

新观点与旧原则冲突时，不直接覆盖：

1. 记录新旧判断、现实约束和证据；
2. 判断变化发生在局部方法还是核心价值；
3. 创建或更新 Decision Log；
4. 只修改真正受影响的长期原则；
5. 检查相关 Prompt、Skill 和工作流是否需要同步；
6. 保留变化理由和复查条件。

这样既不会让旧原则变成永久禁令，也不会让一句新想法立刻改写整个系统。

## 完成标准

一次 Router 调度完成时，使用者应该知道：

- 当前问题怎么看；
- 参考了什么；
- 最大取舍和不确定性是什么；
- 下一步由谁执行、如何验证；
- 结果应该回到哪里；
- 这次内容是否值得进入长期系统。

可直接复制的完整 Prompt 见 [Founder OS Router Prompt](../prompts/founder-os-router.md)。
